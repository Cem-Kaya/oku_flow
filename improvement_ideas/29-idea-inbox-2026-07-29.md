## A. Lecture audio in recordings — IMPLEMENTED 2026-07-29

Advanced Device settings now list Windows microphone endpoints, default new
settings to the system multimedia microphone, and retain an explicit
video-only choice. `AudioCapture` opens only during recording and normalizes
the selected endpoint to 48 kHz mono PCM. Camera and audio arrivals share a
QPC time domain; `RecordingManager` writes the same segment-relative samples
into both original and processed sink writers, where Media Foundation encodes
them as AAC. A hardware-independent mux test verifies that the finalized MP4
contains an audio stream. Remaining owner gate: record and play back a real
microphone with both output files, including one `_partN` camera-mode split.

## B. Camera focus/exposure lock (anti-hunt)

**Problem.** No camera-control code exists (`IAMCameraControl` /
`IAMVideoProcAmp`: zero hits). Phone and UVC cameras autofocus-hunt and
auto-expose; the stabilization fixture *models focus loss as a standard
disturbance* because it happens constantly in practice. Every hunt blurs the
text the magnifier exists to sharpen, and defeats stabilization's sharp
keyframe selection.

**Sketch.** The protocol is UVC Camera Terminal / Processing Unit controls,
surfaced on Windows as `IAMCameraControl`/`IAMVideoProcAmp` (QI the MF
media source); every control is optional and capability-detected via
`GetRange`. Expected support by source class (2026-07-29 assessment —
verify empirically):

| Source | Focus lock | Exposure lock | Fallback |
|---|---|---|---|
| Motorized UVC webcam (C920/Brio class) | yes | yes | — |
| Fixed-focus UVC webcam | n/a | usually | — |
| Pixel/Samsung native USB webcam mode (Android 14+) | likely no — real UVC device, minimal gadget control set | likely no | guide to phone-screen tap-to-lock |
| DroidCam/Iriun/Camo virtual cameras | no via API (not UVC; proprietary stream + virtual driver) | no via API | name the vendor app's own lock feature |

Build: lock toggles + "lock current" one-shot in Device ▸ More; persist per
camera alongside plan 28's map; locks reapply after mode renegotiation
(§E); unsupported cameras get honest per-vendor signposting, never silent
no-ops. **Extend plan 28's stage-1 probe to dump each camera's supported
control set** (a ~30-line `GetRange` sweep) so the matrix above becomes
measured fact on the owner's real devices before UI work starts. UVC 1.5
region-of-interest AE/AF exists but device support is rare — probe for it,
do not design around it.

**Effort:** 2-3 days + camera matrix. **Priority: high** — cheap, directly
improves text clarity *and* stabilization input quality on the cameras
that allow it, with honest guidance on the ones that do not.

## C. Spatial view bookmarks (board left / board right / lectern)

**Problem.** Lecture halls have fixed geometry; a magnifier user pans
between the same 3-4 places all lecture. Nothing persists view positions
(verified: no bookmark/pan storage in `settings_store.cpp`) — every return
to "the left half of the board" is a manual pan at high zoom, which is
exactly when panning is hardest.

**Sketch.** Ctrl+Shift+1..9 saves the current zoom+pan as bookmark N
(announced); 1..9 (or Ctrl+1..9) jumps to it with the existing smooth-motion
path; bookmarks persist per quick-option profile; a small "Bookmarks" row in
the viewport scope of the inspector lists and clears them. Screen-reader
announcements name them ("View 2 saved", "View 2"). Optional later: name
them.

**Effort:** 1-2 days. **Priority: high** — small cost, direct place-keeping
value in the core magnification loop.

## D. Session resilience — crash recovery and "lecture session" resume

**Problem.** A crash or accidental close mid-lecture currently loses: which
camera+mode, zoom/pan, active profile, annotation ink, and whether recording
was running. The student restarts blind, mid-class, under time pressure.
fMP4 already protects recorded *bytes* (plan 20), but nothing restores the
*session*.

**Sketch.** A lightweight session journal (`session.json`, written on
change, atomically): camera, mode, profile, view, recording-active flag,
annotation model snapshot. Clean exit deletes it; startup with a journal
present offers exactly one accessible prompt: "Resume the lecture session
from 14:03? (Enter = yes)" — restoring everything, including *offering* to
restart recording as a new `_partN`-style file. Never auto-record without
the prompt.

**Effort:** 2-3 days. **Priority: high** — turns the worst mid-lecture
failure from a scramble into one keystroke.

## E. Battery and thermal saver mode

**Problem.** The real deployment is a laptop unplugged in a lecture hall
for 1-2 hours, running CUDA + high-refresh presentation continuously. No
power-state handling exists (verified: no battery/power code). A dead
battery at minute 70 is a total product failure for that lecture.

**Sketch.** On `SYSTEM_POWER_STATUS` battery + threshold (or user toggle
"Battery saver" in Viewport scope): cap present rate (120→60/30), drop
superres to the cheap path, lengthen assistive cadence, optionally pause
Extra Stable's costlier passes. Announce the switch once. Measure the
actual watt delta with plan 22/28 stage-0 counters before tuning thresholds
— this seed is UI + plumbing around knobs that already exist.

**Effort:** 2 days after counters exist. **Priority: medium-high.**

## F. Searchable lecture notes — pair every image with its text

**Problem (precise).** OCR full text *does* reach the notes when an OCR run
succeeds (`FinishOcrSuccess` → "Text on screen" section,
`assistive_runtime.cpp:903-916`, deduplicated). The gaps are narrower but
real: photo and annotation **snapshots are appended with an empty text
body** (`AppendNoteSection(heading, {}, filePath)`, `:485-496`), so the
images a student most wants to search — the moments they chose to capture —
carry no text; and the notes file has no index. A screen-reader user cannot
Ctrl+F a PNG.

**Sketch.** When a snapshot/photo is noted, run OCR on the *saved image*
(local Tesseract — no quota) and append the recognized text under it in the
same section; generate a per-lecture index (section headings + first lines)
at the top of the notes file; give each section a wall-clock timestamp
(also the prerequisite for idea Q).

**Effort:** 2 days. **Priority: high** — it converts an existing feature's
output from "viewable" to "usable" for the core audience.

## H. Diagnostics bundle export

**Problem.** When something fails on a user's machine (or yours), evidence
is scattered: qInfo logs go nowhere durable, settings are hand-found in
%APPDATA%, device/driver info requires dxdiag. The crash-forensics workflow
exists only as developer knowledge (WER dumps + offline analysis).

**Sketch.** "Save diagnostics…" in Advanced ▸ More: writes a single zip —
recent log ring, sanitized settings (API keys stripped — plan 23 rule),
negotiated camera formats, adapter/driver versions, pipeline status string,

initiated, nothing transmitted. Pairs with 04 U5 (surface pipeline errors)
and makes remote support of a blind user actually possible ("send me the
file the app just saved").

**Effort:** 1-2 days. **Priority: medium-high** — support leverage grows
with every new user.

# The lecture-day walkthrough — where the flow actually hurts

Ideas A-K came from surveying the backlog. This section walks the user's
day instead, and each pain point either maps to an idea above or produced a
new one (L-Q). The persona: legally blind student, phone clamped to the
laptop, NVDA running, 90-minute lecture, fixed seat.

**Phase 1 — the rushed three minutes before class.** Sit, clamp the phone,
plug USB, launch, aim, zoom — while classmates watch and the lecturer
starts. Pains: *aiming is circular* (you need to see the framing to aim the
camera you need for seeing — → **L**); auto-exposure ruins a
projector-lit board (→ B); every second of setup counts (→ D's session
restore doubles as a fast start; J teaches the ritual once).

**Phase 2 — the ninety minutes.** The core loop is watch → pan → read →
note. Pains: *split attention* — the student alt-tabs to their note-taking
app and the magnified view is gone exactly while they type (→ **M**, the
strongest new idea here); *the slide changes while they read* the previous
one (→ **O**); *reading a dense slide against the clock* — the board won't
wait (→ **N**); *"is it still recording? how much battery?"* anxiety with
no way to ask (→ **P**); returning to the same board regions all lecture
(→ C); battery draining (→ E).

**Phase 3 — after class.** Find the files (plan 21, done), then study: a
90-minute recording is unnavigable without landmarks (→ **Q**), and notes
must be text-searchable (→ F).

## L. Framing assistant (aim the phone without seeing)

Detect the dominant bright quad (the keystone detector already finds
screens) and *announce* framing: "Board detected. Tilted left about 5
degrees. Right edge cut off." — repeat on demand while the user adjusts
the clamp. Reuses existing detection; the new part is turning geometry into
speech. **1-2 days. High — it removes the worst setup pain.**

## M. Compact always-on-top view (magnify while taking notes)

No always-on-top or PiP mode exists (verified — zero
`WindowStaysOnTop` hits). A hotkey collapses OpenZoom into a small
borderless always-on-top strip (user-set corner/size) so the magnified
board stays visible while the student types in Word/OneNote; the same
hotkey restores. Chrome hides, pan/zoom hotkeys keep working globally in
this mode. **2-3 days. High — it fixes the split-attention problem, which
is constant, not occasional.**

## N. Freeze-to-read (hold a sharp frame on demand)

The machinery exists — Extra Stable already presents a held frame during
bumps (`deviceBumpHoldFrame_`, `cuda_interop.hpp:329`); there is no
*user-triggered* hold (verified). One key freezes the sharpest recent
frame for calm reading (screen reader announces "Held"), live view
continues underneath, same key returns; optional auto-snapshot of the held
frame to notes. Recording is never affected (records live). **1-2 days.
High — reading speed under pressure is the mission.**

## O. Region change alerts (the watcher, no ML needed)

"Tell me when the slide changes": luma-difference over the current view
region (or a saved bookmark region), thresholded and debounced, announced
once — a trivial CUDA reduction, not a VLM. This is also the cheap first
rung of the local-VLM "ambient watcher" discussion: prove the interaction
pattern with pixels before spending on models. **1-2 days. Medium-high.**

## P. Status query hotkey (ask the app how it's doing)

One hotkey answers, by announcement: "Recording, 42 minutes, audio level
good, 31 GB free, battery 54%, camera 1080p60, 0 dropped." Screen-reader
users query state instead of scanning UI — today nothing offers this
(plan 20's drop counters and P0 identity make the data available).
**1 day. Medium-high, and trivially testable.**

## Q. Recording chapter markers (navigate the 90 minutes)

Every user event during recording — snapshot, bookmark jump, annotation
save, Read — appends a timestamped chapter entry tied to the recording
timeline (plan 20 P0 timestamps make the correlation exact). Export as a
chapters sidecar next to the MP4 and mirror into the notes ("14:03 —
annotated view"). Study time drops from scrubbing to jumping. **2 days.
High for study workflow; needs F's per-entry timestamps.**

## V. Lecture time machine — live rewind (added 2026-07-30) ⭐

**Problem.** The most common in-lecture failure is temporal, not optical:
the student looks down to type for ten seconds and the board has changed.
Today's options — hope it returns, or wait for the recording after class —
both lose the lecture's thread. Freeze-to-read (N) preserves one instant;
nothing preserves the last half minute.

**Why now.** This week made it cheap: the recording stack writes trustworthy
fMP4 with ~2 s fragment cadence, GPU-fed encoding costs near-zero CPU, and
30 s of 720p H.264 is ~4-8 MB. A rolling encoded ring (in a temp file or
memory) using the *same* `VideoRecorder` machinery with a ring policy gives
DVR semantics without new media code.

**Sketch.** Always-on background encode of the processed view (setting,
default on while a camera runs; battery saver E can disable). One key:
pause live and enter replay — scrub/step through the last N seconds
(15/30/60 s setting) with the existing zoom/pan controls active on the
replayed frames; same key returns to live (which never stopped being
captured). Announce entry/exit. Audio ring included when the mic is
enabled. Optional: "save this moment" appends the replayed clip to the
session recording/notes. Distinct from recording: the ring is ephemeral,
wiped on exit, never written into Recordings.

**Effort:** 4-6 days (ring writer policy, a decode/replay path via
`IMFSourceReader`, replay UI + announcements). **Priority: top of the
feature wave — this is the mission's temporal magnifier, and no other
tool in the space has it.**

# The dev hat — faster to build, safer to ship, cheaper to maintain

## R. Decompose `main_window.cpp` (the current god file)

`OpenZoomApp` was decomposed by plans 02/11; `main_window.cpp` inherited
the growth instead — it is now ~2800+ lines building every panel, the
stylesheet, mode logic, and event routing in one TU, and it appears in
nearly every feature diff (see this week's git status). Split by
responsibility (chrome panels, inspector construction, mode/toast logic,
event filter) behind the existing class; measure compile time before/after
(MSVC Build Insights). **2-3 days, zero behavior change, pays rent on
every future feature.**

## S. Version identity + installer + winget

`project(OpenZoom LANGUAGES CXX)` — **no VERSION exists anywhere**
(verified), so no About box, no "which build are you on?" for support, and
bundles are anonymous zips. Seed: CMake `project(... VERSION x.y.z)` +
git-hash build stamp → About dialog + diagnostics + bundle folder name +
SHA list; then an MSIX/MSI installer and a winget manifest so updates
become `winget upgrade` — the most accessible update path Windows offers
(no custom updater UI to make screen-reader-safe). Pairs with plan 23
signing. **Version: half a day (do immediately). Installer+winget: 2-3
days, pre-release wave.**

## T. Crash capture and durable logs

Today `qInfo`/`qWarning` go to the debugger only and crashes rely on
hand-run WER forensics. Seed: rotating file log (QLoggingCategory sink)
into the plan-21 folder; opt-in WER LocalDumps registry setup from the app;
`build_release_bundle.bat` archives PDBs next to the SHA-256 it already
computes, so any user dump symbolizes a year later. Feeds idea H's bundle.
**1-2 days. Medium-high — support debt compounds with every new user.**

## U. CUDA Graphs for the per-frame kernel chain

The steady-state frame launches many small kernels individually; plan 03
P9 tunes configs but nothing captures the chain as a CUDA Graph (one
launch, lower CPU overhead, better scheduling). Measure first with plan
22/28 stage-0 counters; capture the stable portion of the pipeline as a
graph behind a flag. **2-3 days after counters exist. Medium — do with
plan 22, not before it.**
